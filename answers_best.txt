When step 7 of 10 failed, we chose to resume the same sandbox rather than roll back or start fresh. Since the first six steps had already produced valid artifacts and state, resuming preserved the filesystem and allowed recovery without re-provisioning the VM. Rollback would have required a snapshot before the risky step and risked discarding useful intermediate work, while a fresh start would have been the safest but also the most expensive in both time and cost. The trade-off was added recovery logic, but we kept it auditable by recording a policy_applied event in reports/failure_trace.jsonl.

We relied on two Celesto capabilities: safety_hooks and network_policy. Safety hooks let us inspect and block dangerous commands before they reach the guest, while network_policy enforced an allow-list to constrain outbound traffic. With only a stateless shell, there would be no pre-execution guardrails, no way to enforce egress restrictions, and no persistent audit trail of blocked attempts. In practice, that means prompt injection could be executed directly and any attempt to exfiltrate data would have no deterministic containment.

For our containment test, we deliberately sent a prompt_injection_exfil attempt (curl to an external host). The safety hook blocked the command before execution, and the allow-list network policy added a second layer of defense. Both actions were logged (decision: block in logs/commands.jsonl), and the test confirmed blocked: true with host_untouched: true in reports/containment.json backed by reports/evidence/containment.log. The weakest point we identified was credential/environment injection. If real, long-lived API keys were present in the sandbox, they would be the highest-value target when browsing untrusted content, so we strictly used placeholders and never committed secrets.

We defined success as a fresh sandbox completing the core task end-to-end with its expected proof output and a valid run recorded under execution_target: celesto_sandbox. To separate setup failures from product failures, we tracked sandbox state through creation/boot: failures before reaching ready (provider/SDK errors, boot timeouts) were treated as setup failures, while failures after ready where the agent/tool logic broke mid-task were treated as product failures and recorded as success: false. Every one of the 20 fresh runs used a unique sbx-eval* name, all rows were retained for post-mortem (reports/postmortem.md), and the summary statistics in reports/reliability.json were recomputed directly from those rows.

With five uniquely named sandboxes running concurrently, everything held with no name collisions or observed shared state issues (reports/concurrency.json), and cleanup remained intact across all runs. The main limiter was the free trial’s single-retained-sandbox allowance. Before scaling to much larger fan-out, we would add a job queue with concurrency caps and backpressure, enforce per-job budgets with idle-timeout auto-cleanup, improve resiliency with retry/idempotency and orphan reaping, and harden isolation with stricter per-tenant quotas and cross-job interference tests against shared services like the API and ledger.
