When step 7 of 10 failed, we chose to resume the same sandbox rather than roll back or start fresh. Since steps 1-6 had already produced valid artifacts and state, resuming preserved the filesystem and allowed recovery without re-provisioning the VM. Rollback would have required a snapshot taken before step 7 and risked discarding intermediate valid work, while starting fresh would have been the most expensive in time and cost and would have lost all progress from the first six steps. This added some recovery complexity, but we kept it auditable by recording a policy_applied event with policy "resume" in reports/failure_trace.jsonl.

We relied on two Celesto capabilities: safety_hooks and network_policy. Safety hooks allowed us to inspect and block dangerous commands before they reached the guest, while network_policy enforced an allow-list to constrain outbound traffic. With only a stateless shell, there would be no pre-execution guardrails, no way to enforce egress restrictions, and no persistent audit trail of blocked attempts. That would mean prompt injection could be executed directly and any attempt to exfiltrate data would have no deterministic containment.

For our containment test, we deliberately triggered a prompt_injection_exfil attempt (curl to an external host). The safety hook blocked the command before execution, and the allow-list network policy added a second layer of defense. Both actions were logged as decision: block in logs/commands.jsonl, and the result was recorded as blocked: true and host_untouched: true in reports/containment.json with evidence in reports/evidence/containment.log. The weakest point we identified was credential/environment injection. If real, long-lived API keys were present in the sandbox while browsing untrusted content, they would be the highest-value target, so we used only placeholders, avoided committing secrets, and treated any credential injection as an explicit trust decision.

We defined success as a fresh sandbox completing the core task end-to-end with its expected proof output and a valid run recorded under execution_target: celesto_sandbox. To separate setup failures from product failures, we tracked the sandbox lifecycle: failures before reaching ready (provider/SDK errors or boot timeouts) were classified as setup failures, while failures after reaching ready where the agent/tool logic broke mid-task were classified as product failures and recorded as success: false. All 20 runs used unique sbx-eval* names, every row was retained for post-mortem in reports/postmortem.md, and the summary statistics in reports/reliability.json were recomputed directly from those rows with success_rate, median/p90 wall-clock, median boot-to-ready, and total_cost_usd matching the data.

With five uniquely named sandboxes running concurrently, everything held with no name collisions or observed shared state issues (reports/concurrency.json), and cleanup paths remained intact across success, failure, and interrupt. The main limiter was the free trial's single-retained-sandbox allowance. Before scaling to much larger fan-out, we would add orchestration with a job queue, concurrency caps, and backpressure; enforce per-job budgets with idle-timeout auto-cleanup; improve resiliency with retry/idempotency, orphan detection/reaping, and a cleaner separation between control plane and execution plane; and harden scale safety with stricter per-tenant quotas and tests for cross-job interference against shared services like the API and ledger.
